# git-ritual: a clean way to finish a work session

## Overview

The **git-ritual** is a repeatable process for closing out a session so that the history stays clean and every PR is easy to review. It works whether the session touched one repository or several. The goal is simple: one intent per branch, one logical change per commit, honest attribution, and a PR that a reviewer can understand without asking you anything.

## When to trigger this skill

Run the ritual when the user:

- Says "git ritual", "wrap this up", "commit everything", or "create PRs"
- Has finished a feature or a work session
- Asks for commit messages or a PR description
- Has changes spread across more than one repo that need coordinating

## Start of work: branch hygiene

Before the first edit, file create, or code-changing command in a repo, run the three-step branch dance:

1. `git checkout main` (or the repo's default branch)
2. `git pull` (get the latest from origin)
3. `git checkout -b <meaningful-branch-name>`

Only then start editing.

**Why:** branching off whatever happened to be checked out risks building on stale code, piling unrelated work onto an old feature branch, or creating merge mess later. Starting every change from fresh main with its own purpose-named branch keeps history clean and keeps each PR focused on one thing.

**Branch naming:** describe the change, not the author or the date.

- Good: `feat/user-invites`, `fix/session-timeout`, `cleanup/dead-config`, `refactor/auth-middleware`
- Bad: `my-work`, `patch-1`, `tmp`, `wip`, `new-stuff`

**One branch per intent.** If a branch needs a second unrelated change, start a second branch. When in doubt, split.

**Already on a feature branch from a previous task?** Stop. Go back to main, pull, and branch again. Do not branch off a stale feature branch, it compounds the mess.

**This applies to every repo the session touches.** If the work ends up spanning three repos, each one gets its own three-step dance before its first edit.

## The ritual steps

### Phase 1: Assessment

Before committing anything, get your bearings:

1. **Which repos were touched?** List them.
2. **What changed in each?** Run `git status` and `git diff`. Note the scope and any breaking changes.
3. **What is the narrative?** What was accomplished, how the changes relate, and what problem was solved. This becomes the PR summary.

### Phase 2: Attribution

Every commit gets a co-author trailer so AI collaboration is recorded at the git level, and every PR body ends with a pairing line.

**Commit trailer** (last line of every commit message, preceded by a blank line):

```
Co-Authored-By: Claude <noreply@anthropic.com>
```

Use this exact casing. The capitals in `Co-Authored-By` matter for some tooling, and GitHub surfaces the trailer in the PR UI as a co-author avatar. If you want to record the specific model, you can extend it, for example `Co-Authored-By: Claude (Opus 4.8) <noreply@anthropic.com>`.

**PR description footer** (its own line, at the very end of the PR body):

```
Paired with Claude
```

"Paired with" reads honestly: the human drives direction, Claude executes and suggests, and the commits belong to both. Prefer this over any autogenerated "Generated with" footer.

### Phase 3: Commit messages

Write one commit per logical change. Use a short, conventional-style subject line, a body that explains **why** (the code already shows what), and the co-author trailer.

**Format**

```
<type>: <subject in the imperative, under ~72 chars>

<body: what changed and, more importantly, why. Wrap at ~72 chars.>

Co-Authored-By: Claude <noreply@anthropic.com>
```

**Common types**

- `feat:` new features
- `fix:` bug fixes
- `refactor:` restructuring with no behavior change
- `perf:` performance improvements
- `test:` adding or updating tests
- `docs:` documentation changes
- `style:` formatting only, no logic change
- `build:` build system or dependency changes
- `chore:` housekeeping (tooling, config, cleanup)

**Example: single-purpose fix**

```
fix: add missing file extensions to ES module imports

Node's ES module loader requires explicit extensions on relative
imports. The build emitted extensionless paths, which threw
ERR_MODULE_NOT_FOUND at runtime.

Co-Authored-By: Claude <noreply@anthropic.com>
```

**Example: multi-part feature**

```
feat: add single-use relay links for external posting

Add the schema, endpoints, and admin UI for temporary relay URLs
that let an external client post one item and then expire.

- add relay_sessions and relay_posts tables
- add generate and consume endpoints
- add admin UI to create and revoke relays
- enforce single use: a second consume returns ALREADY_USED

Tested end to end: create, consume, and reuse rejection all pass.

Co-Authored-By: Claude <noreply@anthropic.com>
```

### Phase 4: PR description

For each repo with changes, write a PR body a reviewer can act on without context from you.

**Template**

```markdown
## Summary

[One short paragraph: what this PR does and why.]

## Changes

- [Change 1]
- [Change 2]
- [Change 3]

## Testing

- [ ] [What you ran / verified]
- [ ] [Edge case checked]
- [ ] [Automated tests pass]

## Breaking changes

[List them, or write "None".]

## Related

- Closes #[issue]
- Depends on [PR in another repo, if any]

## Checklist

- [ ] One intent per PR
- [ ] Commits are focused and follow the format
- [ ] Co-author trailer on every commit
- [ ] Tests added or updated
- [ ] Docs updated if needed
- [ ] Breaking changes documented

---

Paired with Claude
```

### Phase 5: Execution

**For each repo:**

1. Review: `git status` and `git diff`
2. Stage the files for one logical change: `git add <files>`
3. Commit with the trailer (use a heredoc so the trailer is part of the first commit, not an amend):

   ```bash
   git commit -m "$(cat <<'EOF'
   feat: short subject

   Body explaining why.

   Co-Authored-By: Claude <noreply@anthropic.com>
   EOF
   )"
   ```

4. Repeat 2 to 3 until the working tree is clean and each commit is one logical change.
5. Push: `git push -u origin <branch-name>`
6. Open the PR with the prepared description (`gh pr create` or the GitHub UI).

**Multi-repo coordination**

- Use consistent branch names across repos where the work is one effort.
- Note cross-repo dependencies in each PR's "Related" section.
- Merge foundation changes first (schema, API), then dependents (UI, clients).

## Best practices

1. **One logical change per commit.** Do not mix unrelated changes. Each commit should tell a small, complete story.
2. **Explain why in the body.** The diff shows what changed; the message should say why.
3. **Test before committing.** Builds succeed, tests pass, the thing actually works.
4. **Keep PRs focused.** One feature or fix per PR. Split large changes.
5. **Document breaking changes** prominently, with a migration note if needed.

## Special cases

**Emergency hotfix**

```
fix: [brief description of the urgent fix]

Critical fix for [issue]. [What was broken and how this resolves it.]

Co-Authored-By: Claude <noreply@anthropic.com>
```

**Work in progress**

```
wip: [what is being worked on]

Not ready for review. [Current state and what is left.]

Co-Authored-By: Claude <noreply@anthropic.com>
```

**Revert**

```
revert: [what is being reverted]

Reverts [sha] because [reason].

Co-Authored-By: Claude <noreply@anthropic.com>
```

## Troubleshooting

**Forgot the co-author trailer**

```bash
git commit --amend
# add the Co-Authored-By line, preceded by a blank line
```

**Need to split a commit**

```bash
git reset HEAD~1        # undo the commit, keep the changes
git add <first set>
git commit -m "..."     # commit in smaller logical pieces
git add <second set>
git commit -m "..."
```

## Summary

The git-ritual ensures that when a session ends:

- All work is committed in focused, well-described pieces
- Branches and PRs each carry one intent
- Collaboration is attributed at the git level
- PRs are complete enough to review without a conversation
- Cross-repo changes are coordinated in the right order
